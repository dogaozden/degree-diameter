# table-audit: what checks out in the published bipartite table

Scope: the 112 cells of the bipartite degree–diameter table (Δ 3..16, D 3..10) as recorded in
`research/frontier/TABLE.md` and `heuristic.py` `TABLE`. One row per cell is in `audit.csv`
(columns: delta, D, table, status, holder, ours, graph_file, n, rebuilt, check, notes), generated by `build_audit.py`
from `cells.csv` (`inventory.py`), `moore_results.txt` (`moore.py`, `check_moore.sh`) and `records_check.csv`
(`check_records.py`).

"Rebuilt yes" means: a graph of order at least the table value is in hand, and `apsp.c` (or `apsp_mt.c` with 4 threads)
reports it bipartite, with max degree ≤ Δ, connected and diameter ≤ D. The check is on graphs, not on the holders'
own constructions.

## Findings to act on

1. **Holders are not traced per cell.** The wiki (combinatoricswiki.org) could not be read from the container again
   (TLS and HTTP 503), so the wiki's colour key is unread. The holder column is the survey's general attribution
   (TABLE.md "Who holds what") plus the eight cells named in the README. Nothing here confirms who first built any
   value except where a repo file or the README says so.
2. **Stale values in the code.** `research/frontier/heuristic.py` `TABLE` still has (13,3)=270 and (15,3)=370 (2013
   survey). TABLE.md and the README use the wiki's 2022 values, 274 and 374. The inventory uses 274 and 374. The
   README "Table" column agrees with 274 and 374 for all 69 parsed rows.
3. **Our records exceed the table value, but that is not the table's construction.** For the 69 beaten cells, our
   record is a witness that the table value is a lower bound. The original construction behind each table value
   (Hafner, Loz et al., Delorme–Farhi, Araujo-Pardo–López) was not rebuilt. Only the records' own graphs were checked.
4. **Unbeaten cells with no traceable construction.** (6,5)=684, (3,7)=168, (16,7)=4,022,340, (4,8)=2,184,
   (10,8)=1,176,480, (12,8)=4,650,100, (14,8)=14,172,480, (16,8)=36,201,060, (3,9)=506, (4,9)=4,970, (3,10)=800,
   (15,10)=2,300,326,510, (16,10)=4,119,507,330. Our best value is below each of these, and no graph of the table
   order is in the repo. The holder is not known from the sources read here.
5. **(11,10)** is unreadable in the survey PDF text. No value is assumed and no construction is traced.

## Method notes

- `apsp.c` is the reference checker. `apsp_mt.c` (4 threads) was used for graphs above 50,000 vertices; it runs the
  same checks.
- Moore graphs: PG(2,q) and W(q) incidence graphs were built by `moore.py` (own GF(q) code, own symplectic
  form). The D=6 hexagon H(q) incidence graphs were built by the lab's `research/evenq/hexq.py`; the apsp check is
  what counts for those.
- Record graphs: JSON records and edge lists were converted to plain edge lists and checked as they are. Large
  D=6, D=8 and D=9 graphs (up to 1,092,960 vertices) were checked with `apsp_mt.c`.
- Not done: `.sol` generator files (for example `research/frontier/sols/*.sol`) were not run through their builders;
  the Lean data files (`lean/BipartiteDD/Graphs/*.lean`) were not parsed.
