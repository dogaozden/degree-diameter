# bigcheck-dist: checks that split into parts

Project brief: [BRIEF.md](BRIEF.md). Handoff notes: [HANDOFF.md](HANDOFF.md).

## 1. What bcd does

`bcd.c` checks "bipartite, max degree ≤ d, diameter ≤ D" for a graph with known symmetries, and splits the work into
parts that can run on different machines (or cloud sessions) and be merged afterwards.

Two inputs:

| mode | graph | symmetry used | memory |
|---|---|---|---|
| `explicit` | an edge list (apsp.c text format, or binary `BCDE1`) | permutation generators (`perm ...` or `shift L B`, the level shift of apsp_orb.c), each checked edge by edge | CSR (4 bytes per edge end) + 24 bytes per vertex |
| `lift` | a cyclic voltage lift: base multigraph with voltages in Z_M, never written out | the Z_M translations (automatic) and base automorphisms `aut u pi c` meaning (v, g) -> (pi v, u g + c(v)), each checked on the base | base only + 24 bytes per lift vertex |
| `lift` with `group sl P N` / `group psl P N` | a lift with voltages in SL(2,P) × Z_N or PSL(2,P) × Z_N, (u, g) ~ (v, s g); Haar graphs are the lifts of the dipole (`haar2lift.py SOL OUT.spec`) | right multiplications (automatic): one source per base vertex | same |

The steps:

1. Read the input (sha256 of the bytes read), check ids, self-loops, repeated edges (lift: two base edges v -> w with
   the same voltage), maximum and minimum degree, bipartiteness (explicit: 2-colouring; lift: 2-colouring of the base,
   which colours the lift).
2. Check every automorphism generator. Explicit: a bijection of V that maps every edge to an edge (binary search in
   sorted adjacency lists). Lift: for every base edge v -> w with voltage a there is a base edge pi v -> pi w with
   voltage u a + c(w) − c(v), degrees agree, u is a unit mod M.
3. Orbits of the generated group on vertices (explicit) or on base vertices (lift) by union-find; the representative of
   an orbit is its smallest member (lift: the lift vertex (rep, 0)). The sorted representative list has a sha256.
4. Part i of K takes the representatives with index in [floor(iR/K), floor((i+1)R/K)). Bit-parallel BFS, 64 sources per
   pass, OpenMP over vertices inside each level (one set of arrays, so memory does not grow with threads).
5. Write a certificate: header (version, mode, input and automorphism sha256, n, edges, degrees, bipartite, d, D, number
   of orbits, representatives sha256, part range), one line `src <rep> ecc <e> unreached <u>` per source, then the part
   verdict. `bcd_merge.py REPS cert0 cert1 ...` checks that all certificates have the same header, that parts 0..K−1
   are each present once with the right ranges, that the sources of part i are exactly REPS[lo:hi], and that every
   source has unreached 0 and ecc ≤ D; then it prints `RESULT VALID d=.. D=.. n=.. diameter=..`.

**Why this is enough.** An automorphism maps BFS balls to BFS balls, so eccentricity is constant on orbits of the group
generated by verified automorphisms; the representatives meet every orbit; so the largest eccentricity among them is
the diameter, and "every source reaches every vertex" is connectivity. For lifts, the translations (v, g) -> (v, g + h)
are automorphisms by the definition of the lift, and a base automorphism that passes step 2 maps lift edges to lift
edges (edge (v, g) ~ (w, g + a) goes to (pi v, u g + c(v)) ~ (pi w, u g + u a + c(w)), which is the lift edge of the
base edge pi v -> pi w with voltage u a + c(w) − c(v)); together they move (v, 0) to every (w, h) with w in the
base orbit of v.

**Independence and reproducibility.** Each part is deterministic: rerunning `bcd ... --part i/K` on the same input gives
the same certificate. A coordinator can therefore rerun any sample of parts on its own machine and compare. The
certificate does not prove anything by itself (it records what the program computed); what it buys is that the
expensive BFS work can be spread over machines and spot-checked.

## 2. Usage

    gcc -O3 -march=native -fopenmp -o bcd bcd.c
    bcd explicit EDGES d D [--aut FILE] [--part i/K] [--threads T] [--cert FILE] [--reps FILE] [--count] [--cost]
    bcd lift SPEC d D [--part i/K] [--threads T] [--cert FILE] [--reps FILE] [--count] [--cost]
    python3 bcd_merge.py REPS.txt part0.cert ... part{K-1}.cert [--expect-input SHA256]

- `--count`: stop after the orbit computation (prints the number of representatives R, to choose K).
- `--reps FILE`: write the representative list (needed by the merge; any part writes the same list).
- `--cost`: stop each BFS after D levels and report the number of (source, vertex) pairs at distance > D (a search
  score; such certificates are refused by the merge).
- With K = 1 the program prints the verdict itself.

Lift spec (text, whitespace-separated):

    bcd-lift 1
    group cyclic M
    vertices NB
    edges E
    u v a          (E lines: lift edges (u, g) ~ (v, g + a mod M))
    aut u          (optional, repeatable: a unit u mod M, then NB entries of pi, then NB offsets c)
    pi(0) ... pi(NB-1)
    c(0) ... c(NB-1)
    end

Automorphism file for explicit mode: lines `perm x0 ... x_{n-1}` or `shift L B` (v -> (v + B) mod LB on [0, LB), fixed
elsewhere), or the binary format `BCDA1` (see the header of bcd.c).

## 3. Running a check across sessions

1. One machine runs `bcd ... --count --reps reps.txt` and picks K so that a part takes a convenient time.
2. Session i (i = 0..K−1) builds the graph from the committed builder, checks the input sha256, runs
   `bcd ... --part i/K --cert part_i.cert`, gzips the certificate and commits it under
   `research/projects/bigcheck-dist/checks/<graph>/` on its own branch.
3. The coordinator collects the certificates, regenerates reps.txt, runs `bcd_merge.py`, and reruns a few parts of its
   own choosing with `bcd_spotcheck.py` (byte-for-byte comparison of the certificates).

**Worker brief (copy, fill in the brackets).**

    You are worker <i> of <K> for a bcd check of <graph> (project bigcheck-dist). Do only this:
    1. git fetch origin master && git checkout -B <your-branch> origin/master
    2. gcc -O3 -march=native -fopenmp -o /tmp/bcd research/projects/bigcheck-dist/bcd.c
    3. Build the input: <builder command>   (expect sha256 <hex>; stop and report if it differs)
    4. /tmp/bcd <mode> <input> <d> <D> [--aut <file>] --part <i>/<K> --threads $(nproc) --cert part<i>.cert
    5. gzip -9 part<i>.cert; commit research/projects/bigcheck-dist/checks/<graph>/part<i>.cert.gz; push.
    Report the last two lines of bcd's output. Never contact anyone; do not edit anything else.

Cost of a part: (number of sources / 64) passes, each about D · (edges) word operations. Examples on this cloud
machine (4 cores):

| graph | n | sources | time |
|---|---:|---:|---:|
| (14,7) 1,774,584, explicit + level shift | 1.77 M | 357,336 | 4 × 2 min (4 parts) |
| q = 5 hexagon lifts over Z_25, lift + torus | 195,300 | 252 | 0.1 s |

## 4. Tests (research/projects/bigcheck-dist/checks/)

- Cyclic Haar graphs and random cyclic lifts of random bases with a rotation automorphism, 8 seeds: bcd lift, bcd
  explicit (with and without automorphisms) and apsp.c give the same diameter, including disconnected cases.
- A lift spec with one voltage changed: the automorphism check fails, as it should.
- (14,7) 1,774,584 (the coordinator's graph, same edge-list sha256): 4 parts, merged, VALID, diameter 7, 357,336
  sources, the same as apsp_orb ([checks/d14D7_n1774584](checks/d14D7_n1774584/README.md)).
- Merge refuses a missing part and a certificate made with --cost.
- d8/sol2spec.py turns an x2s.c solution into a bcd spec (torus and copy-rotation automorphisms included, both checked
  by bcd): an x2s M = 16 solution at q = 5 is VALID (124,992 vertices), and a 5-copy k = 4 solution gets cost 30 from
  bcd and from x2s's own BFS.
- Matrix-group lifts use a direction-optimizing BFS (push while the frontier is under n/64 vertices, then pull, skipping
  vertices every source of the pass has reached); counts are identical to the pure pull version. Speed: (11,9)
  16,792,080 (SL(2,61) × Z37) in 10 s on one thread, haarcheck_sl 6 s.
- Haar graphs as lifts of the dipole (`haar2lift.py`): the records (6,9) 127,296 (SL(2,17) × Z13), (7,9) 462,840,
  (8,8) 239,904, (9,8) 540,360 (PSL families) come out VALID with diameter exactly D (and fail at D − 1); with one
  generator of the (8,8) graph perturbed, bcd and build_haar2.py both report diameter 9, INVALID.

## 5. Limits and next steps

- BFS arrays: 3 words per vertex. The default word has 64 bits (64 sources per pass, 24 bytes per vertex); compile with
  `-DWB=8`, `16` or `32` for 3, 6 or 12 bytes per vertex and 8, 16 or 32 sources per pass (a lift of 2·10⁹ vertices
  fits in 6 GB with WB = 8). Certificates are byte-identical for every WB (tested on the rotation lift and on part 3/2000
  of the (14,7) check).
- Vertex ids are 32-bit (n < 4·10⁹).
- Lift mode supports Z_M and (P)SL(2,P) × Z_N with P prime (element numbering as in research/frontier/haarcheck_sl.c,
  checked by a self-test at start). Base automorphisms are only supported for Z_M. Other groups (GF(p^k) matrices,
  products, metacyclic) would need their arithmetic added.
