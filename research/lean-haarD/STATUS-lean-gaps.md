## How each link to the edge file is checked

- Lift tables (`Graph.lean`, all six lifts): `research/lean-haarD/gen_lift_gaps.py` reads the edge file, checks it is
  simple, `d`-regular, bipartite (colour classes from BFS) and of diameter ≤ D (a bitset check, equivalent to all-pairs
  BFS), writes the neighbour lists and colours as Lean literals, then reads `Graph.lean` back and asserts that its lists
  equal the edge file. The Lean side only sees the same lists.
- Staged levels (`Level01…`, `Levels.lean`, 2,368 / 4,800 / 7,020): `research/lean-haarD/gen_staged_lift.py` computes the
  ball masks of radius 1 … D−1 from the same lists; each radius step is then checked in Lean by `Staged.stepOK`
  (`decide +kernel`), so the data is not trusted.
- Haar (4,7): `research/lean-haarD/gen_d4D7_n864.py` mirrors the Lean group law (`mul`, `inv`, `enc`) in Python, checks
  the group axioms on the whole group (inverses, identity) and on 20,000 random triples (associativity), checks that the
  Haar graph of S under the numbering (A side `enc g`, B side `432 + enc g`, `(g,A) ~ (s g, B)`) equals the edge file,
  and writes the six-letter A- and B-word certificates. Lean re-checks the certificates (`certA_ok`, `certB_ok`,
  `decide +kernel`) and proves the group axioms itself (`mulG_assoc` by `ring` after the `P_add`/`Q_add`/`S_eq_norm`
  identities, which are `decide` facts over `ZMod 16`).

Lean is therefore checking the statements `∃ G : SimpleGraph (Fin n), IsBipartiteDegDiam G Δ D` for the graph whose
neighbour lists are in `Graph.lean` (lifts) or the Haar graph of `S` (4,7). The identity with the edge file is the
generator's check above, the same arrangement as for the (9,5) 3,036 record.

## Memory, and why some proofs are staged

`decide +kernel` on `Fast.checkFast` for one whole graph grows steadily in memory (about 1 GB per 10 s here, machine
16 GB):
- (3,12) 2,368, D = 12: the first build was killed (exit 137) after 126 s; a second run was at 13.5 GB and still growing when I stopped it by hand.
- (10,5) 4,800, D = 5: killed by the guard at 13 GB after 200 s (the process was still growing).
- (11,5) 7,020: the one-shot local test `checkLocal` was killed (exit 137) after 159 s; it runs in two halves
  (`Local0`, `Local1`, combined by `checkLocal_of_split`), as the 2,510 and 3,122 records do.

So (3,12), (10,5) and (11,5) use the staged chain of `Staged.lean`: one module per radius step, each `decide +kernel`.
(3,10), (4,7) and (3,11) fit in one kernel check (3,11 took 95 s; its memory was not measured), so they use `checkFast` directly.

Two build-system notes, for whoever reruns this:
- The Levels literal of a large radius hits the default heartbeat limit as one declaration, so each radius is its own
  `def lev<r>` in its own module (`Level<r>.lean`), with `maxHeartbeats 0` as in `Graphs/G9592_lev*`.
- Lean's default `maxRecDepth` is too small for the 7,020-vertex adjacency literal; `gen_lift_gaps.py` raises it to
  1,000,000 for tables of ≥ 7,000 vertices (and `maxHeartbeats 0` for ≥ 4,000). The committed 810, 1,344 and 2,368
  tables are unchanged by that rule.
- Background jobs do not survive the end of a tool call here, so the builds were run in foreground calls. Each module
  was built with its own `lake build <module>`, one at a time (the sequence scripts are in the job's scratchpad).
